项 内容

评估日期 2026-11-04
评估方法 静态代码检索 + 本机只读实测（PowerShell / netsh / SQLite），不依赖设计文档的自述
一句话结论 这是「图纸 + 沙盘模型」，不是「机器」。界面与信息架构是真的，技术路线基本成立，但真实业务功能为 0 行代码。

1 三层判定

层 判定 依据
L1 界面层 ✅ 真实 14 个页面可渲染、可点击，DOM 约 2600 节点，浅色排版统一，交互流程（向导、二次确认、diff 预览、抽屉）都能走通
L2 交互层 ⚠️ 半真（内存态） 点击有效果，但只改内存里的 JS 对象。全文 fetch / XMLHttpRequest / localStorage / WebSocket / EventSource 出现次数全部为 0——没有任何数据通路，刷新即回到初始状态
L3 业务层 ❌ 未实现 仓库内没有 backend/ 与 frontend/ 目录。改 IP、封禁、采集日志、算审计哈希链——一行都没写

所谓「点一下封禁 IP 就成功了」：代码里是 toast('已执行') 加一句内存赋值，系统防火墙没有任何变化。

3 技术假设实测（本次真正验证的部分）

设计文档里有若干「应该可行」的判断。下面是我在本机实跑的结果——行就是行，不行就是不行。

# 假设 实测命令/方法 结果
1 能枚举网卡 Get-NetAdapter ✅ 成功，返回 3 块网卡（含中文名「蓝牙网络连接」），非管理员也可用
2 能取 IP/掩码/网关 Get-NetIPAddress -AddressFamily IPv4 ✅ 成功，返回 VMnet8 → 192.168.145.1/24 等
3 能读 Windows 安全日志 Get-WinEvent -LogName Security -MaxEvents 1 ❌ 失败：Attempted to perform an unauthorized operation（非管理员）
4 当前是否具备改网卡的权限 IsInRole(Administrator) ❌ ADMIN=False，改 IP 必然返回 ELEVATION_REQUIRED
5 netsh 输出稳定可解析 netsh interface ip show config ⚠️ 本机输出为英文（"DHCP enabled: Yes"），字段名与中文系统完全不同
6 FTS5 trigram 能搜中文 SQLite 3.53.1 建虚拟表实测 ⚠️ 4 字词命中，2 字词漏报（详见下）
7 能打包成便携 exe import PyInstaller ⚠️ 未安装，打包链路未验证（不影响设计成立，只影响交付形态验证）

3.1 检索能力实测（两个真缺陷）

SQLITE 3.53.1
  MATCH '登录失败'      -> 1     ✅ 四字词正常
  MATCH '登录'          -> 0     ❌ 两字词完全搜不到
  MATCH '失败'          -> 0     ❌ 同上
  MATCH '203.0.113'     -> ERR   ❌ fts5: syntax error near "."
  MATCH '"203.0.113"'   -> 1     ✅ 加引号才成立
  LIKE  '%登录%'        -> 1     ✅ 兜底有效

影响：

  • 中文用户极高频输入两字词（登录、失败、告警、封禁），trigram 以 3 字符建索引，两字词一条都搜不到。这是假阴性——比慢严重得多，会让人误判「今天没有攻击」。
  • IP 直接进 MATCH 会抛语法错误，不是搜不到，是接口 500。而 IP 检索恰恰是本平台最高频的查询。

已修正：设计文档 5.4.3 补了两条硬约束（含点号 token 加引号、<3 字符走 LIKE 兜底与查询改写规则），13.2 补了对应技术难点行。这两条不实现，日志检索模块等于不可用。

4 哪些是真能做、哪些有硬约束

能力 可行性 约束条件
资产台账、值班任务、报表、通知 🟢 高 纯 CRUD，无外部依赖，风险最低
审计哈希链 + 只增触发器 🟢 高 SQLite 触发器即可实现，可单测验证
日志检索 🟡 中 需先修 3.1 的两个缺陷；FTS5 索引体积约为原文 3–4 倍
网卡枚举 🟢 已验证 非管理员即可读
改 IP / 回滚 🟡 中 必须管理员；看门狗跨进程还原是这套设计里最难的一段，尚未验证
防火墙封禁 / 主机隔离 🟡 中 必须管理员；隔离自己会断网，靠 allow_mgmt 兜
Windows 事件日志采集 🔴 有条件 必须管理员，实测非管理员直接 unauthorized
IP 溯源情报 🟡 中 要么有外网，要么自备 GeoLite2 离线库；两样都没有就只剩本地日志聚合
内置漏洞扫描 ⛔ 不做 平台定位是防守方，漏洞只做「导入」
APT 归因 ⛔ 不做 文档已明确列为非目标

5 判断：值不值得做

值得，但要认清现在处于哪一步。

  • 设计与原型的价值：把「蓝队每天要干什么」拆成了 14 个模块、42 张表、96 个接口，且关键风险点都标了处置方案（快照回滚、看门狗、审计链、数据范围、离线可用）。这部分是能直接指导编码的，不是空谈。
  • 原型的价值：让评审人在 5 分钟内看懂产品长什么样、流程怎么走。它不能用来向人证明「已经做出了系统」。
  • 风险：如果有人看到这个界面就以为功能已就绪，接上真实数据时会发现检索漏报、改 IP 需要提权、日志读不到——这三点今天已经实测出两个。

最小心可信路径（按这个顺序做，两周内能证明「不是纸上系统」）：

  1. 第 1 天：网卡枚举 + 连通性检测（已实测可行，直接做）。
  2. 第 2–4 天：SQLite 建库 + 日志入库 + 检索（先修 3.1 的两个缺陷，用真实日志跑通 1 万条）。
  3. 第 5–8 天：改 IP + 快照 + 三级验证 + 回滚（必须在管理员权限下跑，这是唯一未验证的高风险段）。
  4. 第 9–12 天：审计哈希链 + 资产台账 + 告警聚合。
  5. 第 13–14 天：打包成便携版，在另一台干净机器上按 11.8 的 7 条走一遍。

一条经验判断：第 3 步（改 IP 并可靠回滚）是整个项目的生死线。它一旦不可靠，产品就从「运维助手」变成「断网工具」，其余 13 个模块做得再好也没人敢用。

位置 原设计 修正

13.2 技术难点 无 新增 4 行：中文短词漏报、含点号关键词语法错、netsh 输出随语言变化、非管理员读不到安全日志

其余设计章节（模块、数据模型、接口、流程、部署）经本轮核对未发现与实测冲突之处；但「未发现冲突」不等于「已验证可用」，业务逻辑仍需按第 5 节的顺序逐段实现并验证。
