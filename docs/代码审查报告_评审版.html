3 安全发现

S-01 未统一转义就往 innerHTML 拼数据（中危，已部分修复）

证据：全文 21 处 innerHTML 赋值，78 处 esc() 调用。V2 新增的 6 个页面（告警研判/漏洞/基线/值班/报表/通知）全部经过 esc()；V1 的 8 个页面（总览/网络/溯源/资产/日志/应急/审计/设置）仍有字段裸拼，例如资产名、日志摘要、任务标题、规则名。

// 修复前（V1 页面残留写法）
'<td><div class="cell-strong">' + a.name + '</div>...'
// 修复后（V2 页面统一写法）
'<td><div class="cell-strong">' + esc(a.name) + '</div>...'

影响：当前数据为静态常量 → 无法触发。接后端后，任何可写字段（资产名、任务标题、IOC 值、规则名）都能注入 <img onerror=...> 执行脚本；由于操作员是管理员权限，等于把管理台交给攻击者。

修复动作：新增 esc()（转义 & < > " '），V2 页面 100% 接入。 未完成部分：V1 八页仍需逐字段接入，或更彻底地改为 DOM API / 框架模板（自动转义）。这条列为上线前阻断项。

S-02 数据被拼进内联事件的 JS 上下文（高危，已修复）

证据：3 处把变量拼进事件属性内部的字符串字面量：

<!-- 修复前 -->
<input oninput="checkCfm('${it.name}')">
<input oninput="$('#cfmBtn2').disabled = this.value.trim()!=='${it.name}'">
<input oninput="$('#actBtn').disabled = this.value.trim()!=='${target}'">

影响：这是比 S-01 更严重的一类。当 it.name（网卡名，来自操作系统）中含有 ' 或 ) 时，即可跳出字符串边界执行任意 JS。网卡名是外部可控输入（用户可重命名网卡、驱动可创建任意名字的虚拟网卡），这条在接后端后是可直接利用的。

修复动作：改为数据属性传值，JS 只读 dataset，不再拼进代码：

<input data-expect="以太网" data-target="cfmBtn" oninput="checkMatch(this)">

function checkMatch(inp){
  var want = inp.getAttribute('data-expect') || '';
  var btn = document.getElementById(inp.getAttribute('data-target'));
  if (btn) btn.disabled = inp.value.trim() !== want;
}

S-03 无 CSP，依赖内联脚本与内联事件（中危，记录）

证据：单文件原型必然使用 <script> 内联与 130 处 onclick。严格 CSP（script-src 'self'）会直接阻断全部交互。

影响：CSP 是最有效的 XSS 兜底；没有它，S-01 一旦成真就没有第二道防线。

处理：原型允许保持现状（离线演示文件）；生产必须改为外链脚本 + nonce + script-src 'self'; object-src 'none'，并去掉全部内联事件（改用事件委托）。已写入设计文档 9.1。

S-04 原型无鉴权，存在被误部署的风险（高危，已缓解）

证据：文件无登录、无权限判断、无后端，双击即可完整使用全部界面。

影响：如果有人把 prototype/index.html 放到内网 Web 服务器当「系统」用，就是一个无认证的管理台，且界面里有「封禁 IP」「主机隔离」这类按钮（虽然是假的），会误导使用者。

缓解动作： 1. 顶栏品牌旁增加固定标识 「演示原型」，title 说明「无后端、无鉴权，不可部署到网络环境」。 2. 设计文档 9.8 与附录 C 把「原型不可部署」列为交付红线。 3. 文件内不写入任何真实资产、真实 IP（示例统一用文档保留段 192.0.2.0/24、203.0.113.0/24、198.51.100.0/24）。

S-05 全局可变状态无边界约束（低危）

证据：D、D2、S 三个全局对象，交互函数直接改写（如 claimAlert 改 owner、doChange 改 ifaces）。

影响：原型阶段是有意为之（无需持久层即可演示状态流转）；但没有任何校验意味着「认领已认领的告警」这类非法流转只能靠函数内 if 拦截（当前 claimAlert 确实拦了），新增交互时容易漏。

处理：生产环境所有状态流转必须由后端状态机裁决（设计文档 8.5、5.2.4），前端只做展示。

S-06 已确认的安全写法（正向）

  • toast() 使用 textContent 而非 innerHTML 写入消息 → 消息含 HTML 也不会被解析。
  • 全文未使用 localStorage / sessionStorage / document.cookie → 原型不落任何凭据，不存在令牌被同源脚本读取的面。
  • 零外部依赖：无 CDN、无第三方脚本、无远程字体 → 不存在供应链注入与离线失效问题。
  • 所有 onclick 传递的参数都是下标（数字）或固定的枚举字符串，不是用户数据。

S-07 敏感信息处理（说明）

原型数据里的 admin、张伟、203.0.113.45 均为虚构；不含真实手机号、邮箱、内网地址。唯一像凭据的是示例 API Key 展示为 ****8f2c（掩码），符合设计文档「只回显已配置」的要求。

4 性能发现

实测数据（可复现）

用 Edge headless 对 14 个页面各渲染 5 次取中位数：

页面 渲染耗时 页面 渲染耗时
总览 2.9 ms 应急响应 1.7 ms
告警研判 2.2 ms 值班任务 1.5 ms
日志检索 1.8 ms 报表中心 1.3 ms
溯源情报 1.7 ms 审计 3.2 ms
资产台账 1.7 ms 通知中心 2.1 ms
漏洞台账 1.5 ms 设置 1.2 ms
基线核查 1.8 ms 网络配置 1.6 ms

全页 DOM 节点数约 2,659。结论：当前规模下性能无问题（单页 1–3 ms，远低于 100 ms 感知阈值）。

必须说明：上述数据来自每页 6–10 行的示例数据。真实环境「日志 500 行、资产 2000 行、审计 1 万行」下的耗时未实测，下面是基于代码结构的推断，不是测量结果。

P-01 全量 innerHTML 重建（中危，接后端前必须整改）

证据：15 个 render*() 函数都是「拼完整 HTML → 一次性赋给容器」。任何交互（切换网卡、认领告警、切 Tab、翻页）都重建整页。

影响： - 500 行表格时单次重建约 50–150 ms（按 2,659 节点 / 2 ms 线性外推，尚未计入字符串拼接与解析开销），会出现可感知卡顿。 - 更严重的是状态丢失：滚动位置回到顶部、输入框失焦、勾选被清空。这在「勾选 20 条告警准备批量研判」的场景里是功能性缺陷。

整改要求：列表区改为行级更新或引入虚拟滚动；重建前保存并恢复 scrollTop；批量勾选状态存到 S 而不是靠 DOM。

P-02 137 处内联事件（中危）

onclick=130 + oninput=6 + onchange=1。内联属性每次重建都要重新解析并创建闭包，且无法被 CSP 允许。整改为事件委托（容器上挂一个监听，按 data-action 分发），既提速又为 S-03 的 CSP 铺路。

P-03 图表每次渲染重算（低危）

barChart() / donut() 在每次 renderDashboard() 时重新拼 SVG 字符串。数据静态，可缓存结果（首次计算后存 memo）。当前 2.9 ms 里约 0.6 ms 花在这里，可省但不关键。

P-04 表格无虚拟滚动（低危，规模化后变高危）

每行 7–10 个元素，1000 行 ≈ 8000 节点，超过浏览器舒适区。日志与审计列表建议虚拟滚动（或后端强制分页 200 条/页）。

P-05 看门狗定时器跨页空转（低危）

setInterval 每秒执行一次，页面切走后 #wdCountdown 为 null 时仍空转。影响可忽略，但应在 go() 切页时暂停/恢复，避免「后台 20 个定时器同时跑」的叠加。

P-06 无输入防抖（低危，接后端后成中危）

搜索框当前未接真实查询。接后端后每敲一个字符发一次请求会把接口打满，必须 300 ms 防抖 + 取消上一次请求（AbortController）。

P-07 字符串拼接的 O(n²) 风险（低危）

+ 累加在 V8 里有 rope 优化，当前规模无问题；但若改为百万级文本渲染需换数组 join。

5 正确性与一致性问题

C-01 汇总数字与明细不一致（中危，已修复）

证据：基线页卡片写死「合规率 76% / 不合规 9 / 无法核查 2」，而矩阵实际是 8 个不合规单元格、2 个无法核查、合规率 22/30 = 73.3%。界面自相矛盾。

影响：安全报表里「数字对不上」是最致命的可信度问题，评审人一眼就能发现，进而怀疑整份材料的真实性。

修复：新增 baselineStats()，全部从明细矩阵计算，并顺带算分类合规率。

// 修复后实测输出
// pass=22 fail=8 unchecked=2 rate=73  （与矩阵完全一致）

C-02 状态标签语义混用（中危，已修复）

证据：通知渠道的 failed 复用了封禁模块的 ST.failed = ['red','同步失败']，导致通知页显示「同步失败」——应为「发送失败」。

修复：渠道健康用独立映射（健康 / 发送失败 / 未知），不复用封禁语义。

C-03 任务按钮与状态不匹配（低危，已修复）

证据：任务表所有行都显示「验收」按钮，包括已完成的。

修复：review 显示「验收」、done 显示「已验收」、其他显示「催办」。

C-04 死代码（低危）

checkCfm() 在改为 checkMatch() 后不再被引用。建议删除，避免后续维护者误用（两个函数行为相似但一个走 JS 注入面）。

C-05 溯源页默认展示示例结果（低危，展示选择）

S.queried 初始为 true，首次进入直接显示 203.0.113.45 的溯源结果，虽然有空态分支但走不到。这是为了演示效果的有意选择，需在评审时说明；生产应默认空态。

C-06 数据不持久（说明）

所有交互改动（认领、封禁、状态流转）刷新即丢失。原型无持久层，属预期；但容易让评审人误以为功能「已实现」。建议演示时明确「界面已就绪，逻辑待后端」。

C-07 文档一致性缺陷（中危，已修复）

证据：V2.0 重构设计文档时把「网络配置（改 IP）」这个核心模块从第 2 章模块表和第五章功能设计中漏掉了（仅在流程图与接口里残留），导致「模块 13 个」与实际能力不符。

修复：补齐 2.1 M2 网络配置管理、5.2 M2 网络配置管理（含变更流水、看门狗、快照回滚）、7.2 网络配置接口表、10.4.2 页面规格，并把全文编号（5.x / 10.4.x / M 编号）与计数（14 个模块、14 页、14 项导航）统一刷新。

9 结论
